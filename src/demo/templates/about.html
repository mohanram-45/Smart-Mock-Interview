About this project

SMART Mock Interview is a local practice tool for technical interviews (machine learning, deep learning, NLP, Python, SQL, data analysis). It is also a research prototype: this page says what is built, how the parts connect, and what has not been shown to work.

How an interview flows

Retrieval (the RAG part)

The question bank is a curated corpus of 666 records (487 frozen v5 records plus 179 approved expansion records), each with a reference answer and key concepts. A retrieval layer loads and verifies it (fingerprints, manifests, quarantine list) and can embed it with all-MiniLM-L6-v2 into a FAISS index with a BM25 baseline.

In this interview app questions are planned by role, topic coverage and a fixed Easy-to-Hard progression from that corpus. Retrieval (MiniLM and FAISS, or the BM25 fallback) only orders candidate questions, for example against a job description; it never grades a candidate. The separate /api/retrieval routes expose the same search. Its benchmark labels are AI-generated, not human ground truth.

1. Similarity score

Compares your answer's text with the reference answer using Sentence-BERT cosine similarity. It is the only scorer new interviews use. (The earlier Bi-LSTM and TF-IDF scorers remain in the repository for stored sessions and research evidence.)

Limits: it measures resemblance. A correct answer in different words can score low; an answer that borrows the reference's vocabulary can score high. For code it compares text, not behaviour. It has not been checked against human marking. The comment shown with it depends only on the score band.

2. Modular evaluation EXPERIMENTAL

Opt-in. A local model (Ollama, qwen2.5:7b) labels which required concepts your answer states, each backed by a quote from your answer. Fixed rules turn that into a rubric, and a number appears only for the few questions where the scope allows it.

Limits: the recorded 20-answer run failed its acceptance gate (abstain rate 0.45, limit 0.40), so the project's decision is do not advance. It never influences question selection.

3. Code check EXPERIMENTAL

Opt-in, for two Python questions. It separates code from your written explanation, reads the code (parsing only) and reports which required parts are present, missing, incorrect or unverified. Behaviour tests exist but run only inside a locked-down container you set up yourself; otherwise the page says the code was read, not run.

Limits: "found in the code" is not proof it works; explanation checks match wording only and are always unverified. No score is given.

What is and is not established

  • Built and tested: the interview flow, session saving and recovery, the Sentence-BERT similarity scorer, the corpus loader and retrieval index, the opt-in evaluator and the static code check (automated tests plus real-browser runs).
  • Not established: that any score matches human judgement; that the modular evaluator is reliable enough to use; that behaviour tests are safe against hostile code (a container shares the host's kernel).
  • By design: nothing here controls adaptive difficulty, and follow-ups are fixed, bank-backed prompts rather than generated text. Your answers stay on this computer and are deleted after 14 days, or when you delete them.
